\section{Use Case 1: Multiple Ollama Instances}
\label{sec:multi-ollama}

\subsection{Problem Statement}
\label{subsec:multi-ollama-problem}

\begin{itemize}
    \item Small language models may not saturate an entire GPU when served by a single Ollama instance.
    \item A single inference queue may introduce head-of-line blocking, causing short requests to wait behind longer requests.
\end{itemize}

\subsection{Architecture Overview}
\label{subsec:multi-ollama-architecture}

\begin{itemize}
    \item Describe the DRA claim templates and the deployment of multiple Ollama instances on separate MIG devices.
    \item Document the selected model, the load generator, the request profile, and the collection of application- and GPU-level metrics.
\end{itemize}

\subsection{Testing Methodology}
\label{subsec:multi-ollama-methodology}

\begin{itemize}
    \item Establish a baseline consisting of one Ollama instance using the entire GPU.
    \item Evaluate time sharing as an alternative GPU-sharing mechanism.
    \item Evaluate the effect of restricting one Ollama instance to a smaller MIG profile.
    \item Evaluate multiple concurrent Ollama instances assigned to separate MIG devices.
\end{itemize}

\subsection{Results and Evaluation}
\label{subsec:multi-ollama-results}

\begin{itemize}
    \item Compare the measured throughput, latency, GPU utilization, and energy-related metrics across the evaluated configurations.
    \item Discuss why workload-aware right-sizing of MIG instances is critical to obtaining a net benefit.
    \item Distinguish the performance gains produced by MIG-based consolidation from DRA's role as a provisioning mechanism in this use case.
    \item Motivate the need for a workload in which resource requirements vary across executions and can therefore benefit from dynamic allocation.
\end{itemize}

\section{Use Case 2: Kueue-Managed Batch Workloads}
\label{sec:kueue-use-case}

\subsection{Problem Statement}
\label{subsec:kueue-problem}

\begin{itemize}
    \item The finite lifecycle of batch jobs aligns naturally with DRA claims, because resources can be selected for each execution and released when a job terminates.
    \item Kueue priorities determine admission precedence but do not, by themselves, guarantee a job's execution time or end-to-end service level.
    \item Introduce service classes that combine scheduling priority with workload-appropriate GPU or MIG allocation policies.
\end{itemize}

\subsection{Kueue Background}
\label{subsec:kueue-background}

\begin{itemize}
    \item Explain Kueue's purpose and its principal concepts for queueing and admitting Kubernetes batch workloads.
    \item Describe priority management in Kueue and its interaction with resource availability, quotas, and workload admission.
\end{itemize}

\subsection{Architecture Overview}
\label{subsec:kueue-architecture}

\begin{itemize}
    \item Define service classes through combinations of Kueue priorities, DRA device classes, and resource claim templates.
    \item Motivate the selected conservative and aggressive resource-allocation policies.
    \item Describe the heterogeneous job pool, its workload profiles, submission process, and resource lifecycle.
    \item Define the experimental scenarios: a Gold workload assigned to a medium MIG profile, a Gold workload assigned to a large MIG profile, a static mixed-workload baseline, and the dynamic D-Flex policy.
\end{itemize}

\subsection{Results and Evaluation}
\label{subsec:kueue-results}

\begin{itemize}
    \item Compare admission delay, job completion time, throughput, GPU utilization, energy-related metrics, and consolidation density across the baseline and dynamic scenarios.
    \item Evaluate whether matching each job profile to an appropriate DRA-managed MIG device provides a measurable advantage over static allocation.
    \item Discuss the trade-offs among service differentiation, resource efficiency, predictability, and operational complexity.
\end{itemize}
